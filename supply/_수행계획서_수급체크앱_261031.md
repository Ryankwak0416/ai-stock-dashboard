## 03. 키움 API 접속 경로 (0단계에서 결정)

확인된 것
- 이 Claude 클라우드 컨테이너에서는 `api.kiwoom.com`·`mockapi.kiwoom.com` 접속이 프록시에서 차단된다(2026-10-31 curl, 403). 키움 호출은 이 컨테이너가 아니라 GitHub Actions 또는 사무실 PC에서 해야 한다.
- 저장소 안에 키움 관련 코드·설정은 아직 없다. 연결된 GitHub 저장소 4개, 지난 클라우드·PC 세션 12개 기록에도 키움 설치·사용 흔적이 없다. 2026-10-17 세션에서는 "IP 등록 문제로 이번엔 적용하지 않음"으로 보류됐다. → **키움은 아직 GitHub에 등록되지 않은 상태**로 판단한다.
- 이 컨테이너는 네이버·다음 접속도 막혀 있다. 모든 수집 시험은 GitHub Actions(`supply-probe.yml`, claude/** 브랜치 push로 실행)에서 하고, 로그를 받아 판단한다.

진행 원칙(261031 개정): 키움이 들어올 때까지 기다리지 않는다. 공개 원천으로 먼저 돌아가는 앱을 만들고, 키움 키가 들어오면 같은 `data.json`의 해당 항목이 키움 값으로 자동 승격되게 한다(항목마다 `source` 표기).

확인 필요
- 키움 REST API는 사용할 PC의 IP를 미리 등록하는 구조로 보인다(최대 10개). 근거는 2차 자료인 wikidocs.net/342465와 algolab.co.kr/kiwoom-rest-key-guide이고, 공식 포털 openapi.kiwoom.com에서 확인해야 한다.
- GitHub Actions 러너는 해외·유동 IP라, IP 등록이 필수면 Actions에서 직접 호출하는 경로는 막힌다.
- 건축사님이 쓰는 것이 REST API인지 OpenAPI+(윈도우 OCX)인지 확인해야 한다.

경로 후보
- A. GitHub Actions 직접 호출: 기존 방식 그대로다. IP 제한이 없을 때만 가능하다.
- B. 사무실 PC를 GitHub self-hosted runner로 등록 **(유력)**: 워크플로 파일은 그대로 두고 `runs-on`만 바꾼다. PC 고정 IP를 키움에 등록한다. 장중에 PC가 켜져 있어야 한다. OpenAPI+라면 이 경로만 가능하다(32비트 파이썬 + 로그인 유지).
- C. 국내 고정 IP 클라우드 VM: PC에 의존하지 않지만 월 비용이 생긴다.
- D. PC 단독 스크립트: 러너 없이 PC 작업 스케줄러가 키움 수집 → `supply/kiwoom.json` 만 GitHub에 push. Actions 수집기가 그 파일을 읽어 합친다. 러너 등록이 부담스러울 때 쓴다.

판단 기준: 0단계 probe 결과(토큰 발급 성공 여부와 실패 사유).

## 05. 단계별 할 일과 합격 기준

### 0단계 — 접속 확인
- 건축사님 확인: ① REST인지 OpenAPI+인지 ② 실전·모의 중 어느 키인지 ③ 키움에 등록된 IP(사무실 PC인지).
- 건축사님이 키를 GitHub Secrets(`KIWOOM_APPKEY`, `KIWOOM_SECRETKEY`)에 직접 등록한다(브라우저에서 저장소 Settings → Secrets and variables → Actions). Claude는 키 값을 받지도, 보지도 않는다.
- 수동 실행용 `probe-kiwoom.yml`을 만든다: 토큰 발급 + 코스피 투자자별 1건 조회. 키와 토큰은 로그에 찍지 않는다.
- 작업 에이전트: 04의 1~6번에 맞는 TR의 요청·응답 필드 표를 만든다.
- 합격: Actions에서 토큰 발급과 1건 조회가 성공하면 A로 간다. 실패 사유가 IP로 확인되면 B 또는 C로 정하고 계획서를 개정한다.

### 1단계 — 장마감 수집기
- `supply/collect_supply.py`: `money/collect_money.py` 패턴을 재사용한다(재시도, 날짜별 캐시, 오류 누적, 부분 실패 허용).
- `supply.yml`: 평일 18:50 KST, concurrency `main-content`, push 재시도 루프.
- 키움이 실패하면 네이버 3주체로 대체하고 `data.json`에 `source` 표기를 남긴다.
- 합격: 3거래일 연속 자동 수집. 코스피·코스닥 개인·외국인·기관 합계(억원)가 네이버 값과 일치하고 오류는 0.

### 2단계 — 화면
- `supply/index.html`: Chart.js 4.5.0, Pretendard, money 앱과 같은 카드·색 체계.
- 구성:
  ① 오늘 요약(주체별 순매수 + 한 줄 신호)
  ② 60일 누적 순매수
  ③ 기관 세부
  ④ 프로그램 차익·비차익
  ⑤ 업종별 외국인·기관 순매수
  ⑥ 종목 순위(클릭하면 `timing/?code=` 연결)
  ⑦ 공매도·신용
  ⑧ 갱신 시각·오류·원천
- 합격: 폰 폭(390px)과 PC에서 렌더 스크린샷 확인, 가로 스크롤 없음, 데이터가 비어도 깨지지 않음.

### 3단계 — 장중 확장
- 평일 09:30~15:30에 30분 간격으로 수집한다. 결과는 `supply/intraday/YYYY-MM-DD.json`이고 최근 20일만 유지한다.
- GitHub schedule 누락에 대비해 `update.yml`처럼 2회 시도한다(B 경로면 PC 작업 스케줄러도 가능).
- 합격: 하루 장중 회차의 80% 이상 수집. 마지막 회차 값이 장마감 확정값과 크게 다르지 않음.

### 4단계 — 연결·운영
- money 앱 상단에 수급 앱 링크 1줄을 넣는다(유일한 기존 앱 수정).
- 수집이 2거래일 연속 실패하면 화면에 경고를 띄운다(선택: 카카오 나에게 보내기).
- 합격: 1주 무인 운영, 오류 0.

## 06. 위험·주의

- 공개 저장소: 키는 Secrets에만 둔다. 워크플로에서 `echo`를 금지하고, fork PR에서는 secrets가 넘어가지 않는 기본값을 유지한다.
- 호출 한도: 키움 초당 호출 제한은 확인이 필요하다. 호출 간격을 0.25초 이상 두고 재시도한다.
- 저장소 크기: 장중 30분 커밋이 쌓이므로 intraday는 최근 20일만 보관한다.
- push 충돌: `money-flow.yml`에는 concurrency 그룹이 없다. 새 워크플로는 `main-content` 그룹 + 재시도 루프로 충돌을 피한다(money-flow는 손대지 않음).
